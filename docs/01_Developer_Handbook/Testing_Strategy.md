# Testing Strategy

## 1. Why This Exists

If you write a new feature for AgileWriter, how do you know you didn't break something else? You run the tests. 

But this repository does not use traditional Unit Tests (where a single function is tested in isolation). Instead, this suite uses **End-to-End (E2E) Tests** and **Data Accuracy Pipelines**. This document explains the different types of tests we use, what they actually measure, and when you should use them.

## 2. Mental Model

Think of our testing strategy as having two completely separate halves:

1. **Health Tests (The "Does it crash?" test)**
   These tests pretend to be a human user. They open a browser, click buttons, and upload files. If the document generation finishes and a file is produced, the test passes. It **does not care** if the generated text is garbage. It only proves the system is alive.

2. **Accuracy Validations (The "Is it right?" test)**
   These tests do not use a browser. They take the Word documents generated by the Health Tests and read every paragraph, comparing the text against a "Known Good" answer key. If the AI hallucinates or misses a section, this pipeline catches it.

## 3. Real Examples

### Example: Health Tests
All Health tests live in the `tests/` directory and use the `health_*.spec.ts` naming convention.
* **Definition**: An End-to-End browser automation script.
* **Why it exists**: To verify that the core document paths (like creating a CSR or an ICF) execute successfully from the UI down to the backend and back.
* **Repository example**: `tests/health_CSR.spec.ts`
* **When to use it**: After every deployment, to ensure the environment is stable.
* **When NOT to use it**: If you need to verify that a specific AI prompt change improved the quality of the generated text.

### Example: Accuracy Validations
The accuracy pipeline lives in the `benchmarking_automation/` directory.
* **Definition**: A Python pipeline that extracts text from DOCX files and scores it.
* **Why it exists**: To catch regressions in AI model quality.
* **Repository example**: `benchmarking_automation/main.py`
* **When to use it**: When data scientists release a new model or prompt template.
* **When NOT to use it**: If the environment is completely broken and you can't even log in.

### Example: Fixtures and Mocking (And why we don't use them)
* **Definition**: A **fixture** is a fixed piece of test data. **Mocking** is faking a system response instead of actually calling the real system.
* **Why we DON'T use mocking**: We are testing AgileWriter from the outside in. If we mock the AI training response, we aren't actually testing AgileWriter; we're just testing our own mock. Therefore, these tests execute against the *real* QA environment, uploading *real* files, and waiting for *real* AI training.

## 4. Step-by-Step Workflow: The Validation Lifecycle

A typical release validation looks like this:

1. **Deploy** AgileWriter to the QA environment.
2. **Run Health Tests**: A QA Engineer opens `localhost:3000/ui` and runs `health_CSR.spec.ts`.
3. **Wait**: The test drives the browser and waits 20 minutes for the CSR to generate.
4. **Pass/Fail**: If it passes, we know the system works mechanically. The generated `.docx` artifact is saved.
5. **Run Accuracy Pipeline**: A developer runs `python benchmarking_automation/main.py`, feeding it the `.docx` artifact from step 4.
6. **Review Scores**: The pipeline generates a color-coded Excel report comparing the new artifact to the baseline.

## 5. Common Mistakes

* **Treating Health Tests as Accuracy Tests**: A green checkmark on a health test ONLY means the document generated. It does not mean the document is correct. 
* **Running Health Tests on Production**: These tests upload files and trigger expensive AI training. They are designed for QA/UAT environments (configured via `.env` `BASE_URL`).

## 6. Troubleshooting

**Symptom**: Your Accuracy Validation pipeline is failing with a schema mismatch.
* **Diagnosis**: The structure of the generated Word document changed (e.g., a table was added or a header was renamed). 
* **Fix**: You need to update the parser in the Python pipeline (`benchmarking_automation/doc_parser/`) to understand the new document format.

## 7. Key Takeaways

* **Health Tests** = Node.js + Playwright + UI. Fast to fail, slow to run. Proves the system is alive.
* **Accuracy Validations** = Python + Data extraction. Proves the AI is smart.
* We do not use Unit Tests or Mocking in this repository because our goal is true End-to-End integration testing against a live environment.
